What changed, and when

Every change to the protocol, the data, published findings and the site itself — newest first, each entry linking to the evidence it rests on. Entries older than this page live in the notes and the dataset release notes on Zenodo; nothing before 2026-09-03 was retroactively reconstructed.

2026-10-25site

One-liner run.sh with a hardened security model

quantenergy.tech/run.sh is now a 20-line stub that downloads the real wrapper from the immutable release run-v1 (ecocompute-mlcube), verifies its embedded SHA-256, then executes — a DNS hijack of the site cannot change what runs. The container page documents both paths (four-line audited vs one-liner convenience) under the same pinned-release security model. Homepage, contribute and replications pages link the one-liner.

2026-10-24api

CI gains a daily heartbeat: the deploy-vs-repo checks keep running while the site itself is frozen

The live probes in CI (deployed-Worker drift, /mcp smoke, UA matrix, rate-limit and funnel canaries) were all push-triggered — which means they only ran when the repo changed. The repo is now in a deliberate freeze (no feature work; only responses to new PRs and external replies), so the probes would have gone dark exactly when nobody is watching the code. The workflow now also runs on a daily schedule (01:23 UTC, off the hour to dodge GitHub's scheduler congestion). One line of YAML, no Worker changes, no redeploy — but the "deployed state still matches the repo" defense line no longer depends on the repo being active.

2026-10-24api

MCP calls now feed the first-party funnel — registry-driven distribution is finally measurable

Since the registry listing, assistants can call the estimator over /mcp — but those calls were invisible to the /v1/track funnel, systematically understating distribution. The Worker now records mcp_initialize (client name) and mcp_tool_call (tool, ok, and whitelisted scalars: params_b/arch/precision/batch/ctx) server-side into the same FUNNEL KV, same row shape as the site beacon. Free-text arguments (q, query) are deliberately never stored — the no-PII rule is unchanged. While verifying this, the FUNNEL namespace turned out to be completely empty — funnel events have been silently not landing (cause under investigation; the event TTL was lowered from 400 to 364 days as the prime suspect). CI now runs a funnel canary on every push so this failure class cannot hide again, plus a sustained-rate /mcp probe (~4 req/s for ~40 s) — the per-IP limiter is permissive and eventually consistent per Cloudflare's docs (a sub-second burst passes clean, observed), so it is checked in the regime it actually guards.

2026-10-24api

Custom-domain attempt knocked workers.dev 404 for ~5 minutes; restored, and the UA matrix says the endpoint is client-friendly

Incident: attempting to attach mcp.quantenergy.tech as a Worker Custom Domain failed — the quantenergy.tech zone lives on DNSPod, not in the Cloudflare account, and the partially-applied trigger update took the entire workers.dev route 404 (REST and /mcp, the registry-listed URL) for roughly five minutes until a redeploy without the routes block restored it. CI re-verified after recovery: the REST drift check and all four MCP tools answer correctly again. The wrangler config now carries a warning comment: do not re-add [[routes]] until the zone migrates to Cloudflare. What the outage motivated: a CI UA probe against the deployed /mcp (informational, runs every push) — python-urllib, node, undici, axios, and a generic mcp-client UA all get 200 with a working initialize handshake; only an empty User-Agent is 403'd. So the earlier fear that Cloudflare bot rules on workers.dev might block real MCP clients does not hold in practice — the registry URL is reachable from every realistic client UA we probed.

2026-10-24api

server.json in the repo: the MCP registry listing is now reproducible

api/server.json describes the listing for the official MCP Registry: io.github.hongping-zh/ecocompute-estimator, one streamable-http remote pointing at the live /mcp endpoint. One semantic worth pinning down before it matters: the registry version (1.0.0) is the tool-surface version of the endpoint — deliberately decoupled from the container / dataset versioning. It bumps only when the tool surface changes (a tool added, an output schema changed); the registry uses it to detect updates, and each published version is immutable. The dataset and container keep their own version lines, untouched by registry publishes. Verified against the current registry schema (2025-12-11): remotes[].type = "streamable-http" is the accepted enum value.

2026-10-24site

The Worker now speaks MCP (Model Context Protocol) at POST /mcp — stateless streamable HTTP, JSON-RPC 2.0, no key. Four tools: estimate_quantization_energy (ΔE% vs FP16 with basis and confidence), get_quantization_crossover (per-architecture crossover, with the "card + software stack, not architecture constant" warning), list_data_coverage (measured / borrowed / gaps — "no data for your GPU" as a first-class answer), and search_measurements (the raw anchors behind the curves). Architecture: the seam to a future service layer is now documented — contract only, nothing implemented

An external design review proposed separating the project into a public research layer (this site: static pages, Apache-2.0/CC-BY code and data, immutable DOIs) and a product/service layer (benchmark submissions, report generation, private results). 2026-10-11site

curl | bash retired: the quickstart is now a verified release asset, the image runs non-root

An external security review flagged the documented entry point — piping a moving main branch into a shell — as the site's most urgent fix. Agreed, and fixed at the source (ecocompute-mlcube schema-1.3-r4), then on every page that taught the old pattern: the homepage run command, the container page, and both Chinese guides. The documented way in is now download → verify → run against an immutable release: curl -fsSLO …/releases/download/schema-1.3-r4/quickstart.sh, curl -fsSLO …/SHA256SUMS, sha256sum -c SHA256SUMS, bash quickstart.sh. What executes is a specific, checksummed version — not whatever main holds at the moment you type the command.

The release also carries the rest of the review's list: a CycloneDX SBOM generated from the pinned requirements.lock.txt; the image digest for pinning instead of the mutable :latest (sha256:5c812e66…e275, built by CI with the non-root smoke test green); the container now runs non-root (unprivileged default user; the script has always passed --user $(id -u):$(id -g)); ECOCOMPUTE_READONLY=1 optionally adds --read-only + a tmpfs /tmp, leaving only the two bind mounts writable; and bash quickstart.sh --dry-run prints the complete plan — mode, every directory it would touch on your host, the exact commands — and executes nothing. The script header now states in full what it changes on the host and what it never touches. No measurement, protocol or schema semantics changed: the validator and the pinned dependency set are byte-identical to schema-1.3-r2.

And one defect found on the way, now corrected: the schema-1.3-r1 pins were computed over Windows working-tree bytes (CRLF) instead of the repository blobs (LF). Its schema pin never verified against what raw.githubusercontent.com serves, and its quickstart.sh asset carries CRLF line endings — which makes bash quickstart.sh fail on Linux at set -euo pipefail. A correction is appended to the r1 release notes, and the spec's §5.1 pin table now pins r3 — including the schema's actual LF-blob hash, which the r1 pin had wrong.

2026-09-30datafinding

Four anchors re-measured on their own stack, two months later: 7B holds to a point, 1.5B does not

The cells the Ada curve leans hardest on — Qwen2-1.5B and Qwen2-7B at NF4 and INT8 — were re-run on the same software stack they were originally measured on (torch 2.4.1+cu121, transformers 4.46.3, bitsandbytes 0.45.5, accelerate 1.0.1, the 2026-07-24 configuration), on another rented RTX 4090, two months later. Holding the kernel versions fixed does not remove the drift — it sorts it by model size. Against the July values (−28.46%, +49.54%, +15.11%, +180.73%), this session reads: NF4 7B −28.25% (0.2 points away), INT8 7B +50.75% (1.2 points), NF4 1.5B +22.6% (7.5 points), INT8 1.5B +197.05% (16.3 points). The two trials on which each cell rests were ~48 minutes apart on one card and agree to 0.1–4.5 points, so the gap to July is several times the row's own within-session noise.

What this licenses, and what it does not. It licenses saying that the n = 1 risk in this dataset is concentrated at the small end: at 7B the same configuration returns to about a point across two months and two rented hosts, while at 1.5B the same configuration can move by more than fifteen points with no version change to attribute it to — inside a cell whose published range already spans −28% to +199%. It does not license folding these rows into the published curves, and it does not answer the question left open on 2026-09-25 (whether the full Ada crossover moves under the current stack) — this session repeated the July stack, so that question stands.

Published as a separate versioned session, not pooled into the seed counts, the anchor set or the fitted curves — same policy as every session since 2026-09-20. Data: data/rtx4090_anchor_2026-09-30.csv (+ .summary.csv, generator script). Two disclosures travel with it: the reports are schema-valid but not protocol-conformant — they carry no measurement-window, decoding or arm-order record (the arm order FP16 → NF4 → INT8 is recovered from timestamps, fixed, not randomized); and card identity plus the 36 °C start temperature come from one environment snapshot for the whole session, not per-run logs, so this is within-session trial replication — not across-restart, and not across cards, replication. No existing number changed. One correction elsewhere on the site comes out of it: /method/ used to say that no two sessions ran the same torch build. Since this one, that is no longer true.

2026-09-28site

An external evaluation caught a real ambiguity: the coverage-matrix notes attributed the NF4 crossing point to GPU architecture alone (2.1B Turing / 3.7B Ada / 4.8B Blackwell), while the 5090 re-test section attributed it to software stack alone ("a property of the software stack, not of the architecture"). 2026-09-27protocolsite

Validator hardening: a negative probe that passed as "protocol-conformant" can no longer exist

A hand-built report — non-NVML method, iterations: 1, no window statement, no decoding record, no arm order, a thermal block with only mode and basis — sailed through the semantic validator as protocol violations: 0 / protocol-conformant. That broke the machine-verifiable-core claim, so the validator was rebuilt around one rule: a report that does not record a protocol-required fact is schema-valid, never protocol-conformant. Now enforced (release schema-1.3-r2, commit 8778c42, validator SHA-256 3dc166d2…10bee3, schema itself unchanged): NVML method and ≥ 10 Hz (§4.1.1/4.1.2); the FP16-baseline rule covers every non-FP16 precision (§4.2.1); 256 tokens, 10 iterations and greedy decoding must be present and correct (§4.3.2); the window must be stated as generation (§4.4.1); conformance is floored at schema 1.2+ (§4.5.2); measured thermal blocks need warm-up, cooldown and start/end/peak temperatures, with the steady temperature excused only by an honest steady_state_reached: false (§4.6.1/4.6.4); arm order must be recorded or the deviation disclosed (§4.6.2). The probe itself is pinned as a regression test; the suite is 20/20. Honest consequence: the container does not yet emit the window/decoding/arm-order records, so its own reports are schema-valid only until it does — same status as the thermal block, tracked together. §5.1 pins updated.

2026-09-26siteprotocol

The last spec↔display gaps close: thermal mode on every matrix cell, one replication vocabulary, a stated version of record

  • Coverage matrix cells now carry their thermal mode (t = c/s/u, next to n). 2026-09-26protocolsite

Protocol errata: measurement algorithm pinned, arm order a MUST, references pinned by checksum

Four clarifications to the specification, folded into the site edition (the Zenodo snapshot predates them; they merge into v1.2):

  • §4.1 measurement algorithm is now fully specified — trapezoidal integration over the sampler thread's clock, energy spanning first-to-last sample with no edge extrapolation, dropped reads counted and reported (fewer than two usable samples ⇒ discard), and the pooled-ratio iteration aggregation E/token = ΣE/Σtokens. All five items describe exactly what the reference container does.
  • §4.6.2 arm order: SHOULD → MUST. Order and thermal state demonstrably move results, so randomised or counterbalanced order is now mandatory; a fixed order is a disclosed deviation.
  • Level C renamed "Standard-candidate" (was "v1.0-grade" — confusing next to protocol v1.1), and the document status is now "stable core / candidate specification" rather than plain "stable".
  • §5.1 pinned artifacts — release tag schema-1.3-r1, commit, SHA-256 checksums of the schema and validator, and the image digest, so a conformance claim is a claim against immutable pins, not a moving main. The container quickstart gains ECOCOMPUTE_REF and a checksummed release variant replaces curl | bash on main for reproducible runs.

Site polish in the same pass: the homepage mobile nav is now a proper menu button (nothing truncated), button time-notes sit below their titles instead of side-by-side, and two absolute phrasings are softened ("Nobody measures…" → "Few open tools measure…"; "Every number is reproducible" → "every published measurement is accompanied by its reproducibility artifacts").

2026-09-26protocolsite

The spec–schema loop is closed: schema-valid is no longer mistaken for protocol-conformant

The public energy.schema.json checked structure only — a report could pass it while violating Protocol v1.1 (no thermal block, no same-session FP16 baseline, arbitrary version strings, sample_rate_hz below 10 Hz). Two layers now close that gap in the container repo: the schema itself is tightened (version-enum and const fields, minimum 10 Hz sampling, and at schema 1.3 the workload/measurement/software MUST-fields become required — no existing valid report breaks), and a new semantic validator (ecocompute validate --profile v1.1-core) checks every machine-checkable §4 MUST with clause-numbered violations and CI exit codes. The compliance levels are renamed to say what they actually check: Schema-valid / Protocol-conformant / Dataset-eligible (A/B/C unchanged in substance; see /schema/ §3 and the spec §5). One honest consequence, stated rather than hidden: the 2026-09-25 two-card re-test reports themselves grade as schema-valid but not protocol-conformant — the container does not yet emit the thermal block (tracked issue), and the validator's test suite pins exactly that verdict.

2026-09-25protocol

The spec layer becomes a standalone, DOI-tracked specification document

Protocol v1.1 is extracted from the method page into an independent normative document — EcoCompute Protocol v1.1 — written in the W3C-Note / IETF-RFC style: explicit MUST / SHOULD / MAY requirements for the power source (NVML GPU-package, ≥ 10 Hz), the same-session FP16 baseline, the workload (batch 1, 256 tokens), the generation window and the report fields; SHOULD-level replication (n ≥ 2, n travels with the data); MAY-level extras (additional modes/batches/formats, the draft environment block), each labelled and never pooled. The document binds the protocol to the machine contract — a conforming submission MUST pass ecocompute-energy/1.2+ validation — and carries the protocol ↔ schema ↔ dataset version table. The document is archived on Zenodo at DOI 10.5281/zenodo.22958675 (concept: 10.5281/zenodo.22958674) so papers can cite "EcoCompute Protocol v1.1, DOI: 10.5281/zenodo.22958675" instead of a moving web page; dataset DOIs and the protocol DOI stay separate. The method page remains the human-readable guide and now states that the normative text is the document. Source: spec/ in the site repository.

2026-09-25data

RTX 4090 NF4 re-tested across two physical cards: July's +0.8% anchor holds

Qwen2.5-3B NF4 vs FP16, three independent sessions across two physical RTX 4090s (different UUIDs), current stack (torch 2.14.0, CUDA 13.0, bitsandbytes 0.50.2 — the same stack as the 2026-09-20 RTX 5090 re-test): +3.5% / +0.7% / +0.5%, mean +1.6%. Conclusions: the July n = 1 +0.8% anchor is confirmed (Ada 3B is break-even to a small penalty); the −15.1% from the 2026-08-19 paired-quality session was not reproduced in three current-stack sessions — its stack and conditions differ from the present run and no specific error was identified, so it is retained as a divergent historical observation and excluded from current-stack conclusions; and at the 3B anchor the RTX 5090's stack flip (crossover ≈5B → ≈1.8B) did not appear on the RTX 4090 — only that one anchor was re-measured, and whether the full Ada crossover curve moves under the current stack awaits the 1.5B and 7B points. Observed gaps: the two cards differ by ≈ 2.8 points, the two sessions on card 2 by ≈ 0.2 points (card 1 was measured once, so this is a description, not a variance decomposition; for card-population questions ncard = 2).

Kept as a separate versioned archive (data/rtx4090_bnb_2026-09-25.csv, with power-trace sidecars and the generator script) — not pooled into the seed counts or the fitted curves, per the same versioning policy as the RTX 5090 re-test. Stack differs from the published pins (bitsandbytes 0.50.2 ≠ 0.43.3), so vs_fp16 is not directly comparable with image runs; the reports say so.

2026-09-20datafinding

The RTX 5090 crossover moved from ≈5B to ≈1.8B on a current stack

Re-measuring the same RTX 5090 months later, on bitsandbytes 0.50.2 / torch 2.14 / CUDA 13.0, moved the NF4 break-even size from ≈5B to ≈1.8B — nothing about the hardware changed. A crossover is a property of the software stack, not only of the architecture. 22 runs, n = 2 across a full instance restart; the two sessions agree to 2.1 points on average, 5.2 at worst. INT8 stayed positive at every size (+55% at 7B, +256% at 0.5B). A torchao FP8 companion sweep found both FP8 code paths (weight-only, dynamic activation+weight) more expensive than FP16 at every size, failing in opposite directions.

Maintained as a separate archive — not pooled into the seed counts or the fitted curves, which still describe the 0.4x-era stack: pooling the two would produce a crossover neither session measured. Data: rtx5090_bnb_2026-09-20.csv, rtx5090_fp8_torchao_2026-09-20.csv; raw reports archived at 10.5281/zenodo.22855133.

2026-09-03finding

The kernel decides the sign, not the bit width

Inside one runtime on one RTX 4090: llama.cpp GGUF Q4_0 decoding Llama-3.1-8B-Instruct costs 61.9% less energy per token than GGUF F16 (for +5.60% perplexity) — the quantized arms draw more power (296–319 W vs 273 W) and win purely on throughput. On the same card, bitsandbytes LLM.int8() costs 106% more. Same idea, opposite sign: format-level claims ("4-bit saves energy") are meaningless without the kernel. Corrected the same day over 45 runs (n = 5, randomized order, cooldown before every run, hardware energy counter): the provisional −63.6% was an overestimate.

Note: the note and raw data (10.5281/zenodo.22295184) predate the 2026-09-24 window unification; where the two disagree on a number, the window-comparison CSV is authoritative.
